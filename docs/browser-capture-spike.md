# 技術検証：内蔵ブラウザの通信キャプチャ（v0.3）

| 項目     | 内容                                                                        |
| -------- | --------------------------------------------------------------------------- |
| 状態     | **調査のみ・PoC 未実施**（2026-11 時点）                                    |
| 目的     | WebView2 で発生した HTTP 通信を取得し、API テスターに取り込めるかを確認する |
| 検証環境 | Windows 11 実機が必要（開発用の Linux コンテナでは WebView2 を動かせない）  |

この文書は、公式ドキュメントと既知の API 仕様に基づく **調査メモ** です。各項目は PoC で実際に確認するまで「未検証」とします。

## 1. 候補となる取得方法

### A. WebView2 の標準イベント

| API                                                                                 | 取得できる情報（想定）                                                                      | 注意点                                                                                                                                                                                    |
| ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CoreWebView2.WebResourceRequested`（`AddWebResourceRequestedFilter` で対象を指定） | URL、メソッド、リクエストヘッダー、リクエストボディ（`Content` ストリーム）                 | 本来はリクエストを横取りして応答を差し替えるための API。全リクエストを対象にすると性能に影響する可能性がある。ネットワーク層が後から付けるヘッダー（Cookie など）は含まれない可能性がある |
| `CoreWebView2.WebResourceResponseReceived`                                          | 実際に送信したリクエストヘッダー、ステータス、レスポンスヘッダー、本文（`GetContentAsync`） | 本文はリダイレクトなどで取得できない場合がある。タイミング情報は限定的                                                                                                                    |

### B. Chrome DevTools Protocol（CDP）

WebView2 の `CallDevToolsProtocolMethodAsync` と `GetDevToolsProtocolEventReceiver` で利用する。

| CDP                                                      | 用途                                                             |
| -------------------------------------------------------- | ---------------------------------------------------------------- |
| `Network.enable`                                         | 通信イベントの購読を開始する                                     |
| `Network.requestWillBeSent`                              | URL、メソッド、ヘッダー、POST データの有無、開始時刻             |
| `Network.requestWillBeSentExtraInfo`                     | Cookie を含む、実際に送信した生のヘッダー                        |
| `Network.responseReceived` / `responseReceivedExtraInfo` | ステータス、レスポンスヘッダー、タイミング                       |
| `Network.loadingFinished` / `loadingFailed`              | 完了・失敗、受信サイズ                                           |
| `Network.getRequestPostData`                             | POST ボディ                                                      |
| `Network.getResponseBody`                                | レスポンス本文（完了後、ブラウザが保持している間だけ取得できる） |

**現時点の見込み**：A は取得できる情報が不足する可能性があるため、B（CDP）を主軸に検証する。A は B が使えない場合の代替とする。

## 2. Tauri 2 との統合（想定）

- `tauri::Webview::with_webview` で、Windows ではプラットフォーム固有の WebView（`ICoreWebView2Controller`）にアクセスできる。`webview2-com` クレートを使い、Tauri が依存しているバージョンに合わせる
- 1 つのウィンドウに複数の WebView を置く API（`Window::add_child`）は、Tauri 2 では `unstable` 機能の扱いである。PoC では **ブラウザ用に別ウィンドウ（`WebviewWindow`）を開く** 方式から始め、安定性を確認してから同一ウィンドウへの埋め込みを検討する
- 取得した通信は Rust 側で `HttpExchange`（`source: Browser`）に変換し、既存の共通モデルに載せる

## 3. セキュリティ上の設計方針（案）

- **ブラウザ用 WebView には IPC 権限を与えない。** capabilities はメインウィンドウのラベルにだけ紐付け、リモートの Web ページから Reqit のコマンドを呼べないようにする
- 取得した Cookie や `Authorization` などはメモリ上だけで保持し、明示的に「API テスターで開く」を実行したときだけ引き継ぐ
- 一覧表示では秘密情報らしい値をマスクする（`secrets::redact_spec` を再利用する）
- キャプチャデータをディスクに保存する場合は、v0.2 の履歴と同じく秘密情報を分離する
- ブラウザ用のデータフォルダー（Cookie やキャッシュ）は Reqit 専用にし、ユーザーが削除できるようにする

## 4. 取得と再現は別の問題

通信を取得できても、Reqit から同じ結果を再現できるとは限らない。主な理由を UI でも説明する。

| 要因          | 内容                                                                                                                        |
| ------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Cookie        | HttpOnly Cookie は CDP の ExtraInfo でしか見えない可能性がある。期限切れのセッションでは再現できない                        |
| CSRF トークン | 1 回限りのトークンは再送信で拒否される                                                                                      |
| CORS          | Reqit の送信はネイティブ通信のため CORS の制約を受けない。そのため、ブラウザでは失敗する通信が Reqit では成功することがある |
| 禁止ヘッダー  | `Host`、`Content-Length`、`Connection`、HTTP/2 の疑似ヘッダー（`:authority` など）は除外して再構成する                      |
| リダイレクト  | ブラウザが自動で追従した一連の通信を、どの時点から再送信するかを選べるようにする                                            |
| 認証状態      | OAuth のリダイレクトや、短期間で失効するトークンは再現できない場合がある                                                    |
